# 題材の帳簿 — ①題材のチャットは、まずここから始める

**2026-09-08 カズヤくん指示。「毎回1から調査をするのはトークンの無駄」。**

これまで①題材のチャットは、ジャンル走査・広域の当たり率・素材の実測を毎回1からやり直していた。
6本目の実行で **YouTube API 約5,830／10,000単位**と、チャット1回ぶんのやり取りを丸ごと使っている。
しかも結果は `analytics/` に置かれ、そこは **`.gitignore` で git 管理外**なので、
次のチャットからは「無かったこと」になっていた。

→ **競合の公開データと素材の実測値だけを、ここ（git 管理下）に貯める。**

⚠️ **`analytics/` を git に載せてはいけない**（このchの内部数字＝再生・維持・CTR が入る）。
ここにあるのは他局の公開データと、Commons/NARA の点数だけ。自分のchの動画は1本も入っていない。

## 次の①題材チャットの手順（この順でやる）

### 0. まず帳簿を読む（API を1単位も使わない）
```bash
python tools/theme_ledger.py table              # 全部
python tools/theme_ledger.py table --only-open  # まだ採否が付いていない題材だけ
```
**保留（△）の題材には、次に何を確かめれば決まるかが `note` に書いてある。**
2026-09-08 時点の保留＝**TWA800便**（NTSBドケットの写真点数を数える）・**コロンビア号**・
**テネリフェ空港衝突**（素材未測）・**ラジウムガールズ**・**ゴイアニア被曝**。
🔴 **ここで決まるなら、走査も広域も回さなくてよい。**

### 1. 母集団を更新する（約430単位）
帳簿の保留を全部つぶしても決まらないとき、または前回から3か月以上あいたときだけ。
```bash
python tools/yt_genre_scan.py channels --min-subs 3000 --max-channels 16
python tools/yt_genre_scan.py scan --themes analytics/themes/ep5_keywords.json \
       --out ep7_genre --dump ep7_pool
python tools/theme_ledger.py merge --pool analytics/themes/ep7_pool.json
```
- `channels` は**手で足した局を温存する**（`[温存] …` と印字される）。
- `merge` は同じ動画IDなら**新しいほう**を採る（再生数が育っているため）。

### 2. 母集団を掘って、新しい候補を探す
🔴 **候補の名前を自分で思いつくところから始めない。** それをやると
「思いつかなかった題材」は構造上ずっと見えないままになる。
```bash
python tools/theme_ledger.py neighbor --ledger      # 帳簿の全題材を測り直す
python tools/theme_ledger.py neighbor --words キーワード
```
`pool.json` を直接読んで、再生数の上位や公開月ごとの中央値を見るのが早い。

⚠️ **語の網は必ず取りこぼす。** 6本目の実行では
チャレンジャー号（3本→実は204,490）・ウィンズケール（0本→実は219,106）・
マルパッセダム（0本→実は125,081）を取りこぼしていた。**題に事故名が入っていない動画がある。**
逆に、ステーションNC火災の230,447は**別の火災**（1977ビバリーヒルズ）だった。**中身を見る。**

### 3. 需要は「近所比」で足切りする
近所比 ＝ その動画の再生数 ÷ **同じ局が前後45日に出した動画の再生数の中央値**。
素の再生数は「局の大きさ」と「経過日数」を写すので比べられない。

- ⚠️ **本数が少ないと暴れる**（小さい局の1本が7〜99倍を出す）。**順位付けに使わない。**
- ⚠️ **1.0×を割ったら落とす**、という足切りだけに使う。
- 広域の当たり率（`yt_theme_probe`）は窓が**6か月以上前で終わる**ので、
  **直近に伸びた題材を構造上見られない**（キー橋がこれで n=3 になった）。近所比で補う。
- 広域を回すなら、**基準として3本目スレッシャーと5本目SL-1を必ず同じ実行に混ぜる**
  （2026-09-08 の実行では09-07の値と小数点まで一致した＝道具は安定している）。

### 4. 素材を実測する（🔴 ここでいちばん多く落ちる）
```bash
python tools/commons_probe.py cat "Category:…" --depth 2
python tools/nara_probe.py search "…"
```
- **カテゴリ名は当てずっぽうで打たない。** 無いと 0点 と出て「素材が無い」と誤読する
  （TWA800 は `Category:TWA Flight 800` が0点、正解は `…(1996)` で84点）。
- ⚠️ 保存された JSON は `summary` が分類ずみ、`rows` が**生のライセンス名**。混ぜて数えない
  （`Public domain` を `PD` で照合して 0点 と誤って出した）。
- 🔴 **動画（動く素材）を写真とは別の軸で数える。**
  試写でカズヤくん「実際の映像は引き込まれる」。**本レンダは1920×1080なので、
  それ未満の動画は保険にしかならない**（SL-1のブリーフィング映画640×480＝保険扱い）。
- `rows` の `mime` が `video/webm` などのものを数えるのが早い。

### 5. 決まったら帳簿に書き戻す
`ledger.json` の該当題材に `verdict`・`neighbor`・`material`・`reason`・`measured` を書く。
**落とした題材も必ず理由つきで残す**（同じ題材を二度調べないため）。
`updated` と `runs` も更新する。

## 構造の教訓（`ledger.json` の `structure` にも入っている）

- **実質の分かれ目は「米連邦か否か」。** 米連邦機関（NIST/NBS・DOE/AEC・海軍・NTSB・CSB・NASA・
  USACE・USCG）が調査した事故は、報告書ごと写真も実験映像もPD。
  日本・韓国の1990年代以前は事故当日の写真がほぼ例外なく報道機関のRM。欧州も自由な原本が薄い。
- **NARA の `Restricted - Possibly（Copyright）` で題材を落とさない。**
  シリーズ一括の定型文のことがある（SL-1は兄弟299/299で一括＝PDだった）。
- 🔴 **記録映像を使った回は `【映像あり】` をタイトルの先頭に置く**
  （2026-09-08 カズヤくんが4本目に追加・5本目を先頭へ移動）。
- 尺は**下限27分・上限38分**。勝ち帯は35〜50分（1.47倍）だが上限を超えない。
